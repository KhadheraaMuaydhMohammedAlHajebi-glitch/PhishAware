# PhishAware 0.7.0: Unit 7 system testing and maintenance planning

This release adds no feature for participants. It is release 0.6.0 tested at three further levels
(integration, system, and acceptance), with everything corrected that the tests found, and with a
plan for keeping the system working after it is deployed. No participant has used the system yet:
every result in this release comes from scripted sessions, which test the software and say nothing
about learners.

## Read this first: defect D-7

Release 0.6.0 could lose stored answers and damage its database when two server processes wrote at
the same moment. The Unit 6 evaluation had measured that release ten times without a failed request
or a wrong value. The defect appeared when the pipeline was run again on unchanged code, about once
in a million requests there, and a second time while the correction was being tested, when it
damaged the test database.

The cause is a property of the file locks that SQLite uses: a process loses all its locks on a file
when it closes any descriptor of that file. Every request closed its database connection, and now
and then that close fell between SQLite's own check and its `close()`, and cancelled the write lock
that another thread had just taken. The web service now keeps its connections open in a pool for
each process. A test that delays `close()` on the database file by 0.3 ms makes the fault certain
on the earlier code (12 of 200 journeys completed, database damaged) and runs on every push.

**Do not use release 0.6.0 for a pilot.** `docs/test-report.md`, section 6.2, has the full account.

## New for the operator

- **A damaged database is not backed up.** The daily pass checks the snapshot before it encrypts it.
  If the check fails, the pass says what it found, writes no backup, keeps the earlier ones, and the
  jobs service becomes unhealthy after a day. `docs/deployment.md`, section 7.
- **The web service keeps its database connections open.** Stop the `app` and `jobs` services before
  a restore, as the guide has always asked.
- **Less memory.** The web service settled at 66 MiB in a ten-minute test, against 81 MiB before.
- **A maintenance plan.** `docs/maintenance.md` says what is watched and how often, how a report
  becomes a release, and what is done when something goes wrong. The pipeline now also runs every
  Monday.

## Upgrade

From 0.6.0: take a backup, check out `v0.7.0`, build, and start (`docs/deployment.md`, section 8).
The database is brought to schema version 2 when the new release starts. That step changes nothing
that release 0.6.0 reads, so a rollback to 0.6.0 on the same data works, and the pipeline rehearses
the upgrade, the rollback, and the upgrade again. A database that began with release 0.4.0 to 0.5.1
is repaired by the same step (D-5).

## Known limitations

- No participant has used the system. Whether students learn from it is still the open question.
- The tests were written by the developer. The acceptance cases check the requirements; they are not
  acceptance by users.
- D-7 was invisible in 29 load tests. The contention test makes that one fault certain. A different
  fault of the same rarity could still be there.
- The correction avoids the conditions of D-7 inside the application. SQLite is unchanged, and the
  web service must never close a database connection while it serves requests.
- Response times depend on the machine, and the host of the pilot has not been measured.
- The longest test run is ten minutes.
- The live database file is not encrypted by the application; the deployment guide requires disk
  encryption on the host. Backups are encrypted by the application.
- Two of four faults in the tests came from timing on shared machines. A red run without a change
  in the code can happen again; the maintenance plan says what to do then.
